# API_CONTRACTS — проектные контракты (не исполненная OpenAPI спецификация)

Base: `https://veriq.void-rp.ru/api/v1`. OpenAPI generated by FastAPI from typed contracts; `/docs` disabled/public-protected in prod. No implicit trust in tenant header.

## Системные пробы Foundation

- `GET /health/live` возвращает `200 {"status":"ok"}`, пока процесс обслуживает запросы.
- `GET /health/ready` проверяет PostgreSQL и Redis и возвращает `200 {"status":"ok"}` или `503 DEPENDENCY_UNAVAILABLE` в общем формате ошибок. Ответ не кэшируется. Обе пробы обходятся без данных организаций и пользователей.

## Формат ошибок
`{ "error": {"code":"ATTEMPT_CLOSED", "message":"...", "request_id":"uuid", "details":{} } }`; status codes 400/401/403/404/409/422/429; не раскрывать существование чужих tenant объектов. `Idempotency-Key` для creation/submit/commands; optimistic concurrency via `If-Match` или `expected_revision`.

## Identity / tenancy
`POST /auth/register`, `/auth/verify-email`, `/auth/login`, `/auth/mfa/challenge`, `/auth/mfa/recovery`, `/auth/password-reset/request`, `/auth/password-reset/confirm`, `/auth/logout`, `/auth/sessions/revoke`.
`GET /me`; `GET /me/organizations`; `POST /me/active-organization` (контекст только на сервере/session); `GET /organizations/{org_id}/members`; invitations/join-requests/group-codes CRUD with roles.

## Studio
`GET/POST /organizations/{org}/banks`; `POST /banks/{bank}/share`; `GET/POST /banks/{bank}/questions`; `POST /questions/{id}/versions`.
`POST /assessments`; `PATCH /assessments/{id}/draft` with expected_revision; `POST /assessments/{id}/publish`; `GET /assessments/{id}/preview` (only author/staff).
`POST /assignments`, `GET /assignments`, `POST /calendar/events`, `GET /calendar/events?start=&end=&group=`; `POST /assignments/{id}/targets`.

## Attempt lifecycle
- `POST /assignments/{id}/attempts` → idempotently reserve attempt, `preflight_required` may be returned.
- `POST /attempts/{id}/preflight` → agent required/pairing state, start eligibility.
- `POST /attempts/{id}/start` → `attempt_id`, server_now, deadline, version, variant view **without hidden answer keys**.
- `GET /attempts/{id}` → snapshot, confirmed revisions, lease status.
- `PUT /attempts/{id}/answers/{item_id}` with `client_operation_id`, `expected_revision`, payload; reply revision/server_confirmed_at.
- `POST /attempts/{id}/submit` (Idempotency-Key) → queued/under_review/submitted.
- `POST /attempts/{id}/pause|resume|extend|force-submit` → teacher permissions + audit + atomic version check.
- `POST /attempts/{id}/takeover` → new authoritative control lease; for agent-required new pairing when moving devices.
- `GET /attempts/{id}/result` → visibility gated.

Example save request:
```json
{"client_operation_id":"uuid", "expected_revision":2, "answer":{"type":"short_text","value":"42"}}
```
Example success:
```json
{"answer_revision":3,"server_confirmed_at":"2026-11-12T09:00:00Z","attempt_version":9}
```
Error `409 REVISION_CONFLICT` provides sanitized latest answer revision (if authorized); `409 ATTEMPT_CLOSED` if after deadline; `423 TECHNICAL_PAUSE` for strict connectivity policy.

## Agent & Admin
`POST /agent-enrollments` admin with step-up; `POST /agents/enrollment/request` device proof; `POST /agent-enrollment-requests/{id}/approve|reject`.
`GET /agents/me/config`, `POST /agents/events/batch`, `POST /agents/heartbeat` (or secure control channel); `GET /organizations/{org}/devices`; `POST /devices/{id}/commands` allowlisted, TTL.
`POST /attempts/{id}/pairing-code` browser auth; `POST /agents/pairings/redeem` device auth; `POST /attempts/{id}/pairing-confirm` session proof; `POST /proctoring/{id}/viewer-token` actor auth with exact scope; `POST /proctoring/{id}/stop`.
`WSS /api/v1/agents/control` authorized by device key challenge, not student bearer; `WSS /api/v1/attempts/{id}/events` browser authenticated for reconnect and teacher commands.

## Events
Envelope: `event_id`, `kind`, `schema_version`, `server_seq`, `server_at`, `entity_id`, `payload`; resume by last seq; duplicate events ignored.
Kinds: `attempt.timer_updated`, `attempt.paused`, `attempt.resumed`, `answer.confirmed`, `agent.connected`, `agent.disconnected`, `incident.created`, `viewer.joined`, `viewer.left`, `grade.published`.

## Security constraints
Tenant-scoped generated OpenAPI schema; no agent secret in JS; signed opaque one-use pairing grant; local Bridge origin validation and strong anti-CSRF; never put browser auth tokens in `veriq://` URL; short TTL and explicit user gesture; login required for browser side.
No generic remote shell; no arbitrary file fetch by URL; media tokens publish/subscribe permissions limited room, track, short TTL and active disconnect on revoke. Audit viewer join/leave.

## Storage
`GET /admin/storage/summary`, `/admin/backups`, `/admin/storage/cleanup-candidates`, `POST /admin/storage/cleanup-dry-run`, `POST /admin/storage/cleanup-jobs` with step-up and approval, `GET /admin/storage/cleanup-jobs/{id}`; never arbitrary filesystem paths accepted from client.


## Auth Slice 2 — маршруты тестового стенда

| Метод и путь относительно `/api/v1` | JSON | Успех |
|---|---|---|
| POST `/auth/register` | `email`, `password` | `202` без тела, в том числе для существующего адреса |
| POST `/auth/resend-verification` | `email` | `202` без тела для любого корректного адреса |
| POST `/auth/verify-email` | `email`, `proof`, `password` | `204`, без cookie |

Пароль в последнем запросе становится паролем подтверждённого аккаунта. Неизвестный, истёкший, повторно использованный или привязанный к другому адресу proof возвращает один и тот же `400 INVALID_PROOF`. Невалидный JSON и поля вне контракта дают `400 INVALID_REQUEST`, недопустимый пароль — `400 PASSWORD_REJECTED`. Превышение квоты даёт `429` с `Retry-After`, недоступность лимитера или БД — `503`. Ответы Auth используют `Cache-Control: no-store`, а ошибки содержат серверный request ID. Лимиты тестового стенда на 300 секунд — 30 попыток на IP и 10 на адрес для регистрации и проверки, 30 на IP и 3 на адрес для повтора. Категории независимы. Resend сохраняет действующую ссылку. Новое письмо можно получить после истечения предыдущего proof.

GET `/auth/verify-email` показывает изолированную форму и не меняет состояние. Proof находится во фрагменте ссылки, удаляется из адресной строки при загрузке и отправляется только в JSON через POST. Обработчик исключён из OpenAPI. Маршруты регистрируются только при `VERIQ_ENV=test` и `VERIQ_ENABLE_TEST_REGISTRATION=1`.


## Auth Slice 3 — вход и браузерная сессия тестового стенда

- `GET /api/v1/auth/csrf` с заголовком `X-Veriq-CSRF-Bootstrap: 1` возвращает `csrf_token` и устанавливает cookie браузерного nonce. Клиент держит CSRF-токен в памяти и передаёт его в `X-CSRF-Token`.
- `POST /api/v1/auth/login` принимает JSON `email`, `password` и необязательный `organization_id`. Успех — `204` и новая сессионная cookie. Отказ учётных данных или выбранной области — единый `401 INVALID_CREDENTIALS`. При наличии сессионной cookie требуется logout перед новым входом.
- `GET /api/v1/me` возвращает UUID пользователя и выбранной организации, если она есть. Данные сессии берутся из PostgreSQL.
- `POST /api/v1/auth/sessions/rotate` принимает `organization_id` или `null` для сброса выбора. Успех — `204` с новой cookie. Предыдущая сессия отзывается при ротации.
- `POST /api/v1/auth/logout` отзывает текущую сессию. `POST /api/v1/auth/sessions/revoke` отзывает все сессии аккаунта и повышает `credential_version`. При успехе обе cookie удаляются.

Все мутации входа и сессий требуют точного HTTPS Origin и CSRF-токена. Получите новый токен после входа и ротации. Маршруты доступны только при `VERIQ_ENV=test` и `VERIQ_ENABLE_TEST_LOGIN=1`. Вход возвращает `429` с `Retry-After` при ограничении и `503` при отказе зависимостей. Действующие сессии разрешаются без Redis.


## Auth Slice 4 — MFA на HTTPS-стенде

- `POST /api/v1/auth/login` может вернуть `202 {"status":"mfa_required"}` и установить короткоживущую cookie challenge. Получите новый CSRF через существующий bootstrap. Cookie сессии на этом шаге отсутствует.
- `POST /api/v1/auth/mfa/challenge` принимает `code` и необязательный `recovery`. При подтверждении enrollment возвращает `200` с одноразовым списком резервных кодов. В остальных успешных случаях возвращает `204`. Ответ устанавливает сессионную cookie и удаляет challenge.
- `POST /api/v1/auth/mfa/step-up` принимает `purpose` со значением `sensitive` или `factor_disable`. Возвращает `202`, затем выполняется challenge с TOTP. Успех меняет токен и устанавливает пятиминутную свежесть назначения.
- `POST /api/v1/auth/mfa/disable` требует свежий `factor_disable` и отсутствие обязательной политики. Успех отзывает все сессии аккаунта и удаляет cookie. Ошибочный или истёкший challenge возвращает общий `401`, исчерпание лимита — `429`, недоступность Redis — `503`.

Все операции требуют CSRF, Origin и `Cache-Control: no-store`. MFA-маршруты включаются только на уже разрешённом тестовом HTTPS-стенде отдельным флагом.


## Auth Slice 5 — тестовый HTTPS

- `POST /api/v1/auth/password/change` принимает `current_password` и `new_password`. При успехе возвращает `204` и очищает cookie. Неверный текущий пароль, недействующая сессия или отсутствующий обязательный step-up возвращают `401`. Для step-up используйте назначение `password_change`.
- `POST /api/v1/auth/password-reset/request` принимает `email`. Ответ `202` без тела одинаков для существующего и неизвестного корректного адреса.
- `GET /api/v1/auth/password-reset/confirm` показывает форму. `POST` на тот же путь принимает `email`, `proof`, `password`. Успех возвращает `204`, очищает cookie и требует нового входа. Недействительный proof возвращает общий `400 INVALID_PROOF`.

Мутации требуют HTTPS, Origin и действующий `X-CSRF-Token`. Лимиты по IP и идентификатору независимы для смены, запроса reset и его погашения. При исчерпании квоты возвращается `429`, при отказе Redis — `503`.


## Auth Slice 6 — тестовый HTTPS

- `POST /api/v1/auth/mfa/recovery` принимает email и пароль и возвращает одинаковый `202` без идентификатора кейса. Заявка создаётся только после проверки credentials и доверенного источника.
- `POST /api/v1/auth/mfa/recovery/{case}/action` принимает `action`, `operation_id`, для `verify` также `source_id`. Этапы — `verify`, `approve`, `dispute`, `reopen`, `release`. Сотрудник получает ID кейса и источника через доверенный процесс поддержки. Для целевого MFA step-up передаётся `resource_id` кейса. Успех возвращает `204`. Первый release возвращает `200` с секретом capability. Повтор операции секрет не возвращает.
- `POST .../{case}/enrollment` принимает capability, email и пароль и возвращает seed для подключения TOTP. `POST .../{case}/complete` принимает capability и TOTP и возвращает резервные коды. Обычная сессионная cookie не выдаётся.

Все запросы используют Origin, CSRF и `no-store`. Чужой или отсутствующий кейс и недействующее разрешение возвращают одинаковый отказ. Redis закрывает новые операции при недоступности.

## Academic Slice 1 (test HTTPS)

GET and POST /organizations/{organization_id}/academic/{kind} list and create
catalog records. Kind is courses or study_groups. GET and PATCH on the path
with /{id} read and edit a record. POST /{id}/archive archives it.

List accepts archived, query and page, returning items and total with 20 items
per page. Creation accepts title and optional description, with a UUID
Idempotency-Key. Reusing that key with a different body returns 409. PATCH
accepts title, optional description and the last version. Archive accepts the
last version and repeated archive returns the archived record. Responses omit
the internal creation digest. Out-of-scope records and denied requests return
404. Mutation requests use existing browser cookie, Origin and CSRF checks.

Catalog permission codes are academic.catalog.read, academic.catalog.manage
and academic.catalog.archive. Session tenant must match the URL. The explicit
academic test overlay enables endpoints under the existing test Auth gate.

POST /{id}/restore accepts the archived record version and requires read,
archive and manage permissions. The response preserves the ID and advances
the version. A stale version or an already active record returns 409 and
does not append an audit event. Unknown or out-of-scope IDs return 404.
Archived lists include can_restore for rendering the action.

Проект маршрута `POST /organizations/{organization_id}/academic-roster/transfers` относителен к общей базе /api/v1. Контракт согласован с [проектом транзакции Slice 2](../planning/ACADEMIC_STUDIO.md). Реализация маршрута и рабочей команды требует отдельного архитектурного ревью и допуска.

Запрос использует существующую browser cookie, Origin и CSRF-проверки. Обязателен заголовок `Idempotency-Key` с UUID команды. Тело JSON содержит ровно два обязательных UUID-поля:

```json
{"source_interval_id":"00000000-0000-4000-8000-000000000101","target_group_id":"00000000-0000-4000-8000-000000000102"}
```

Дополнительные поля отклоняются. Аккаунт студента, его членство и исходная группа определяются сервером по открытому интервалу. Входные actor, tenant, grant_epoch, время и ID создаваемого интервала не принимаются. Tenant берётся из действующей проверенной сессии и должен совпасть с organization_id пути. Время закрытия источника, открытия цели и события аудита сервер получает один раз внутри транзакции.

После проверки сессии сервер требует действующее членство и актуальную эпоху вызывающего, роль Org Admin либо Teacher и отдельное разрешение `academic.roster.transfer` на обеих группах. Teacher дополнительно требует действующие явные назначения с актуальными эпохами на обе группы. Назначение на дисциплину не открывает группу. Источник должен оставаться открытым, Student — действующим, целевая группа — активной и отличной от исходной в том же tenant. Авторизация и связь интервала с членством повторно проверяются под проектными блокировками перед записью. До успешного COMMIT ответ успеха не отправляется.

Успех — HTTP 201, JSON с `result="transferred"` и `target_interval_id` созданного интервала. Эти два поля составляют полный ответ. Заголовок `Cache-Control: no-store` применяется к успеху и отказам. UUID события аудита и внутренние снимки полномочий в ответ не включаются.

Для этой команды Idempotency-Key связывает попытку с request_id события успеха. Он предотвращает дубликат мутации через проверку открытого источника и уникальность request ID внутри tenant. Повтор после успешной фиксации не создаёт новую запись. Если источник уже закрыт при предварительном поиске, HTTP-граница возвращает 404, даже с тем же ключом и телом. Возврат сохранённого успешного ответа не предусматривается проектом транзакции. Повтор ключа с другим телом также не создаёт второй перевод и возвращает 409 после авторизации. Ключ команды и `error.request_id` различаются по назначению: первый связывает мутацию с аудитом, второй служит диагностике текущего HTTP-запроса. Потеря ответа требует авторизованной сверки состояния клиентом, автоматический повтор мутации отсутствует.

Предварительный поиск по контракту Slice 2 читает только открытый интервал с активным членством. Закрытый источник на этой стадии даёт единый отказ без UUID студента, поэтому 404 не требует чтения истории для дополнительной авторизации. Внутренний конфликт транзакции при закрытом источнике не даёт HTTP-границе права раскрывать его состояние. Если источник был открыт при поиске и доступ к обеим группам подтверждён, но затем источник закрыл конкурентный перевод, повторная проверка возвращает 409 при сохранении доступа. Утрата полномочий имеет приоритет и даёт 404. Ни один из этих отказов не создаёт интервалов или события успеха.

Маршрут использует отдельный префикс academic-roster. Действующий каталог в browser_login.py регистрируется под /organizations/{organization_id}/academic/{kind}, включая вложенные операции с записями. Новый путь отличается сегментом сразу после organization_id и не зависит от порядка регистрации маршрутов. [Маршруты каталога](../apps/api/veriq/browser_login.py)

Все ошибки используют общий envelope error(code,message,request_id,details). Details не содержит чужих UUID, SQLSTATE, SQL-текста, токенов, хешей или внутренних исключений. Проверки доступа предшествуют сообщению о состоянии ресурса.

| Ситуация | Проектный ответ |
|---|---|
| Отсутствующая, отозванная или истёкшая сессия | 401 SESSION_INVALID |
| Неизвестный источник/цель, закрытый источник при предварительном поиске, неактивное членство при этом поиске, чужой tenant, недостаточное разрешение, роль или назначение на любой стороне | 404 RESOURCE_NOT_FOUND с одинаковым нейтральным сообщением |
| Ошибка Origin или CSRF | 403 по действующей общей границе browser Auth |
| Неверный UUID, отсутствующее поле/ключ, лишнее поле | 422 VALIDATION_ERROR без отражения секретных входов |
| После подтверждения доступа к обеим группам: архивная цель, совпадающие группы, пересечение интервалов или повтор request ID при открытом источнике | 409 TRANSFER_CONFLICT |
| Занятая строка NOWAIT, занятый advisory try-lock или закрытие источника после подтверждения доступа; потеря доступа при повторной проверке даёт нейтральный 404 | 409 TRANSFER_CONFLICT с полным откатом |
| Отказ записи рабочего аудита или внутренняя ошибка | 500 INTERNAL_ERROR после полного отката, нейтральное сообщение |

Будущая HTTPS-приёмка TEN-01/AUD-01 выполняется на синтетических A/B в выделенном Compose-проекте. Для Org Admin и Teacher с полномочиями на обе группы проверить 201, ровно один новый интервал, закрытие исходного и одно событие с общим серверным временем. Для каждой комбинации полномочий только на одну группу и каждого отсутствующего назначения проверить 404 и совпадение снимков состава и аудита. Чужие source/target и несовпадение tenant пути дают такой же отказ без раскрытия существования B. Просроченная сессия даёт 401. Повтор ключа и закрытого источника, два конкурентных перевода, оба порядка отзыва и занятые блокировки не создают дубликатов. Принудительный отказ аудита проверяется по независимому соединению PostgreSQL после 500: интервалы и события совпадают со снимком до попытки. Применимые тесты включают Origin/CSRF и отсутствие секретов в ответах и логах. Рабочий аудит, эффективные права и транзакционная авторизация остаются открытыми до отдельного допуска и реализации.

Будущая проверка маршрутизации должна подтвердить, что POST academic-roster/transfers попадает в обработчик перевода, а POST academic/study_groups — в каталог при любом порядке регистрации. Отдельно сравнить 404 для закрытого до первого чтения источника A, неизвестного UUID и источника B. Для повторной команды с уже закрытым источником ожидать тот же 404 без новых записей. На двух соединениях закрыть источник после подтверждения доступа к обеим группам и проверить 409 при сохранении полномочий, затем повторить с отзывом доступа и проверить 404. Для каждого отказа сверить снимки интервалов и отсутствие нового события успеха.
