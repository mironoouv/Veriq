# API_CONTRACTS — проектные контракты (не исполненная OpenAPI спецификация)

Base: `https://veriq.void-rp.ru/api/v1`. OpenAPI generated by FastAPI from typed contracts; `/docs` disabled/public-protected in prod. No implicit trust in tenant header.

## Системные пробы Foundation

- `GET /health/live` возвращает `200 {"status":"ok"}`, пока процесс обслуживает запросы.
- `GET /health/ready` проверяет PostgreSQL и Redis и возвращает `200 {"status":"ok"}` или `503 DEPENDENCY_UNAVAILABLE` в общем формате ошибок. Ответ не кэшируется. Обе пробы обходятся без данных организаций и пользователей.

## Формат ошибок
`{ "error": {"code":"ATTEMPT_CLOSED", "message":"...", "request_id":"uuid", "details":{} } }`; status codes 400/401/403/404/409/422/429; не раскрывать существование чужих tenant объектов. `Idempotency-Key` для creation/submit/commands; optimistic concurrency via `If-Match` или `expected_revision`.

## Identity / tenancy
`POST /auth/register`, `/auth/verify-email`, `/auth/login`, `/auth/mfa/challenge`, `/auth/mfa/recovery`, `/auth/password-reset/request`, `/auth/password-reset/confirm`, `/auth/logout`, `/auth/sessions/revoke`.
`GET /me`; `GET /me/organizations`; `POST /me/active-organization` (контекст только на сервере/session); `GET /organizations/{org_id}/members`; invitations/join-requests/group-codes CRUD with roles.

## Studio
`GET/POST /organizations/{org}/banks`; `POST /banks/{bank}/share`; `GET/POST /banks/{bank}/questions`; `POST /questions/{id}/versions`.
`POST /assessments`; `PATCH /assessments/{id}/draft` with expected_revision; `POST /assessments/{id}/publish`; `GET /assessments/{id}/preview` (only author/staff).
`POST /assignments`, `GET /assignments`, `POST /calendar/events`, `GET /calendar/events?start=&end=&group=`; `POST /assignments/{id}/targets`.

## Attempt lifecycle
- `POST /assignments/{id}/attempts` → idempotently reserve attempt, `preflight_required` may be returned.
- `POST /attempts/{id}/preflight` → agent required/pairing state, start eligibility.
- `POST /attempts/{id}/start` → `attempt_id`, server_now, deadline, version, variant view **without hidden answer keys**.
- `GET /attempts/{id}` → snapshot, confirmed revisions, lease status.
- `PUT /attempts/{id}/answers/{item_id}` with `client_operation_id`, `expected_revision`, payload; reply revision/server_confirmed_at.
- `POST /attempts/{id}/submit` (Idempotency-Key) → queued/under_review/submitted.
- `POST /attempts/{id}/pause|resume|extend|force-submit` → teacher permissions + audit + atomic version check.
- `POST /attempts/{id}/takeover` → new authoritative control lease; for agent-required new pairing when moving devices.
- `GET /attempts/{id}/result` → visibility gated.

Example save request:
```json
{"client_operation_id":"uuid", "expected_revision":2, "answer":{"type":"short_text","value":"42"}}
```
Example success:
```json
{"answer_revision":3,"server_confirmed_at":"2026-11-12T09:00:00Z","attempt_version":9}
```
Error `409 REVISION_CONFLICT` provides sanitized latest answer revision (if authorized); `409 ATTEMPT_CLOSED` if after deadline; `423 TECHNICAL_PAUSE` for strict connectivity policy.

## Agent & Admin
`POST /agent-enrollments` admin with step-up; `POST /agents/enrollment/request` device proof; `POST /agent-enrollment-requests/{id}/approve|reject`.
`GET /agents/me/config`, `POST /agents/events/batch`, `POST /agents/heartbeat` (or secure control channel); `GET /organizations/{org}/devices`; `POST /devices/{id}/commands` allowlisted, TTL.
`POST /attempts/{id}/pairing-code` browser auth; `POST /agents/pairings/redeem` device auth; `POST /attempts/{id}/pairing-confirm` session proof; `POST /proctoring/{id}/viewer-token` actor auth with exact scope; `POST /proctoring/{id}/stop`.
`WSS /api/v1/agents/control` authorized by device key challenge, not student bearer; `WSS /api/v1/attempts/{id}/events` browser authenticated for reconnect and teacher commands.

## Events
Envelope: `event_id`, `kind`, `schema_version`, `server_seq`, `server_at`, `entity_id`, `payload`; resume by last seq; duplicate events ignored.
Kinds: `attempt.timer_updated`, `attempt.paused`, `attempt.resumed`, `answer.confirmed`, `agent.connected`, `agent.disconnected`, `incident.created`, `viewer.joined`, `viewer.left`, `grade.published`.

## Security constraints
Tenant-scoped generated OpenAPI schema; no agent secret in JS; signed opaque one-use pairing grant; local Bridge origin validation and strong anti-CSRF; never put browser auth tokens in `veriq://` URL; short TTL and explicit user gesture; login required for browser side.
No generic remote shell; no arbitrary file fetch by URL; media tokens publish/subscribe permissions limited room, track, short TTL and active disconnect on revoke. Audit viewer join/leave.

## Storage
`GET /admin/storage/summary`, `/admin/backups`, `/admin/storage/cleanup-candidates`, `POST /admin/storage/cleanup-dry-run`, `POST /admin/storage/cleanup-jobs` with step-up and approval, `GET /admin/storage/cleanup-jobs/{id}`; never arbitrary filesystem paths accepted from client.


## Auth Slice 2 — маршруты тестового стенда

| Метод и путь относительно `/api/v1` | JSON | Успех |
|---|---|---|
| POST `/auth/register` | `email`, `password` | `202` без тела, в том числе для существующего адреса |
| POST `/auth/resend-verification` | `email` | `202` без тела для любого корректного адреса |
| POST `/auth/verify-email` | `email`, `proof`, `password` | `204`, без cookie |

Пароль в последнем запросе становится паролем подтверждённого аккаунта. Неизвестный, истёкший, повторно использованный или привязанный к другому адресу proof возвращает один и тот же `400 INVALID_PROOF`. Невалидный JSON и поля вне контракта дают `400 INVALID_REQUEST`, недопустимый пароль — `400 PASSWORD_REJECTED`. Превышение квоты даёт `429` с `Retry-After`, недоступность лимитера или БД — `503`. Ответы Auth используют `Cache-Control: no-store`, а ошибки содержат серверный request ID. Лимиты тестового стенда на 300 секунд — 30 попыток на IP и 10 на адрес для регистрации и проверки, 30 на IP и 3 на адрес для повтора. Категории независимы. Resend сохраняет действующую ссылку. Новое письмо можно получить после истечения предыдущего proof.

GET `/auth/verify-email` показывает изолированную форму и не меняет состояние. Proof находится во фрагменте ссылки, удаляется из адресной строки при загрузке и отправляется только в JSON через POST. Обработчик исключён из OpenAPI. Маршруты регистрируются только при `VERIQ_ENV=test` и `VERIQ_ENABLE_TEST_REGISTRATION=1`.


## Auth Slice 3 — вход и браузерная сессия тестового стенда

- `GET /api/v1/auth/csrf` с заголовком `X-Veriq-CSRF-Bootstrap: 1` возвращает `csrf_token` и устанавливает cookie браузерного nonce. Клиент держит CSRF-токен в памяти и передаёт его в `X-CSRF-Token`.
- `POST /api/v1/auth/login` принимает JSON `email`, `password` и необязательный `organization_id`. Успех — `204` и новая сессионная cookie. Отказ учётных данных или выбранной области — единый `401 INVALID_CREDENTIALS`. При наличии сессионной cookie требуется logout перед новым входом.
- `GET /api/v1/me` возвращает UUID пользователя и выбранной организации, если она есть. Данные сессии берутся из PostgreSQL.
- `POST /api/v1/auth/sessions/rotate` принимает `organization_id` или `null` для сброса выбора. Успех — `204` с новой cookie. Предыдущая сессия отзывается при ротации.
- `POST /api/v1/auth/logout` отзывает текущую сессию. `POST /api/v1/auth/sessions/revoke` отзывает все сессии аккаунта и повышает `credential_version`. При успехе обе cookie удаляются.

Все мутации входа и сессий требуют точного HTTPS Origin и CSRF-токена. Получите новый токен после входа и ротации. Маршруты доступны только при `VERIQ_ENV=test` и `VERIQ_ENABLE_TEST_LOGIN=1`. Вход возвращает `429` с `Retry-After` при ограничении и `503` при отказе зависимостей. Действующие сессии разрешаются без Redis.


## Auth Slice 4 — MFA на HTTPS-стенде

- `POST /api/v1/auth/login` может вернуть `202 {"status":"mfa_required"}` и установить короткоживущую cookie challenge. Получите новый CSRF через существующий bootstrap. Cookie сессии на этом шаге отсутствует.
- `POST /api/v1/auth/mfa/challenge` принимает `code` и необязательный `recovery`. При подтверждении enrollment возвращает `200` с одноразовым списком резервных кодов. В остальных успешных случаях возвращает `204`. Ответ устанавливает сессионную cookie и удаляет challenge.
- `POST /api/v1/auth/mfa/step-up` принимает `purpose` со значением `sensitive` или `factor_disable`. Возвращает `202`, затем выполняется challenge с TOTP. Успех меняет токен и устанавливает пятиминутную свежесть назначения.
- `POST /api/v1/auth/mfa/disable` требует свежий `factor_disable` и отсутствие обязательной политики. Успех отзывает все сессии аккаунта и удаляет cookie. Ошибочный или истёкший challenge возвращает общий `401`, исчерпание лимита — `429`, недоступность Redis — `503`.

Все операции требуют CSRF, Origin и `Cache-Control: no-store`. MFA-маршруты включаются только на уже разрешённом тестовом HTTPS-стенде отдельным флагом.
