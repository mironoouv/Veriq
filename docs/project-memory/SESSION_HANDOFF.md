# Передача контекста

Veriq — мультиарендная платформа для экзаменов с серверным состоянием, опциональным Windows Agent и отдельным Judge. Требования в [VERIQ_SPEC](../VERIQ_SPEC.md), утверждённые решения в [реестре и ADR](DECISIONS.md), порядок работ в [ROADMAP](../../planning/ROADMAP.md).

Foundation 1b принят и объединён в `main`. Он добавил PostgreSQL-очередь системных задач, внутренний Redis и worker с короткой SQL-пробой. См. [результат слияния и проверенные ревизии](PROJECT_STATE.md). При продолжении сверь Git и PR, затем загрузи нужную область из [индекса](CONTEXT_INDEX.md).

Foundation 1a–1d завершены. Доступны внутренние сессии, tenant-изоляция, [Compose overlay](../DEPLOYMENT.md) и [браузерный smoke](../TESTING.md#foundation-1d-browser-smoke). [План Auth & Account Security](../../planning/AUTH_ACCOUNT_SECURITY.md) одобрен. Auth Slice 1–9 приняты в тестовом объёме. Public Auth — NOT READY, SEC-MFA-01 — OPEN. Открытые задачи см. в [KNOWN_ISSUES](KNOWN_ISSUES.md).

Срез передачи на 2026-11-22 привязан к main `276ef1255e8c073e7714ce4dbf28e04d3bcb6d8d`, squash [PR #73](https://github.com/mironoouv/Veriq/pull/73). Текущий этап — Academic & Studio, Slice 2. Каталог Slice 1 реализован, схема мигрирует до 0025. Main содержит закрытые хранилища назначений Teacher и истории состава, чистые политики, автономные SQL-проверки предпосылок и автономные HTTP-компоненты. Рабочий маршрут перевода не зарегистрирован. Контракт полномочий APPROVED и проект рабочей транзакции PROPOSED имеют разные границы допуска. За подробностями обращайся к [профильному плану и матрице архитектурной готовности](../../planning/ACADEMIC_STUDIO.md#архитектурная-готовность-рабочей-транзакции--proposed), [API-контракту](../API_CONTRACTS.md) и [реализованному состоянию](PROJECT_STATE.md).

PR #73 добавил 24 совместных автономных сценария предварительного допуска, адаптера и чистой политики. В записи разработчика подтверждены 145 целевых pytest, Ruff, mypy --strict и git diff --check в окружении из uv.lock. Проверены обе роли, передача подтверждённой идентичности и SessionGate, точные ответы и отсутствие защищённых данных. Сессионная граница и команда синтетические. Эти результаты не завершают [TEN-01 и AUD-01](../ACCEPTANCE.md) для рабочей операции. Команды и границы проверок сохранены в PROJECT_STATE, матрица готовности здесь не дублируется.

GitHub на дату среза подтвердил открытые зависимости: [PR #54](https://github.com/mironoouv/Veriq/pull/54), HEAD `708dc1bc0ebc2ed9e1fc4fac62698d7368e85e6e`, и [PR #61](https://github.com/mironoouv/Veriq/pull/61), HEAD `2fedbd17734dde9e8a9d2ebd3e3886ca6858b784`. Проверка актуальности сессии между чтениями и уточнения связей аудита из этих веток не входят в назначенный main. Расхождение CI PR #61 требует отдельного разрешения в этом PR. Их работу продолжай по соответствующим назначениям.

Точка возобновления рабочей реализации — после разрешения этих зависимостей и отдельного архитектурного допуска на конкретной редакции протокола и схемы аудита. Сначала сверь актуальные Git и PR с этим срезом. Восстановление Docker Desktop необходимо для отложенного прогона совместимости архивирования и восстановления групп. Перед выделенным Compose-прогоном проверь `docker --context desktop-linux info`, используй только синтетические данные и сохраняй контейнеры и тома других задач. Нагрузочные и интеграционные проверки ведутся отдельно.

До включения перевода остаются открыты рабочая транзакционная авторизация обеих групп, актуальность снимков и доказательства сессии, эффективные SQL-права, полный протокол блокировок, рабочий append-only аудит и полная HTTPS-приёмка TEN-01/AUD-01. Рабочая реализация требует отдельного ревью и допуска. Остаточный риск прежних полномочий доверенной SQL-роли сохраняется. Обязательные checks, production, process и postgres-audit проверяются на опубликованном HEAD каждого изменения. Для этой документальной правки результаты CI ожидаются после публикации контроллером.
