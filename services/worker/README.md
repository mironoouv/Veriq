# Worker

Foundation 1b запускает отдельный процесс из того же образа, что и API.
Миграция `0002` добавляет системную таблицу `background_jobs`. Состояние задач,
счётчик попыток и уникальные идентификаторы хранятся в PostgreSQL. Redis хранит
ограниченную очередь сигналов пробуждения. При потере Redis worker опрашивает
PostgreSQL и автоматически восстанавливает работу с Redis. Redis не публикует порт.

Worker резервирует задачи через `FOR UPDATE SKIP LOCKED`, выполняет SQL-обработчик
и фиксирует его результат в одной транзакции. Повторная постановка с тем же UUID
безопасна. При ошибке обработчик откатывается до savepoint. До трёх попыток
выполняются с интервалами 2 и 4 секунды. PostgreSQL ограничивает каждый SQL-запрос
тремя секундами. При гибели процесса незавершённая транзакция откатывается и
задача снова доступна. Сбой Redis не отменяет уже зафиксированную постановку.
Readiness API возвращает 503 при потере Redis, liveness остаётся доступной.

Доступна только внутренняя SQL-проба. Для уведомлений с внешними эффектами
понадобятся отдельные ограничения времени и ключи идемпотентности у провайдера.
Перед эксплуатацией потребуется политика хранения завершённых задач.
Недоверенные Code/SQL задания будут исполняться на отдельном Judge согласно ТЗ.

Для интеграционного теста запустите одноразовый Compose-проект с именем
`veriq-*` и отдельным портом, задав `COMPOSE_PROJECT_NAME` и `VERIQ_WEB_PORT`.
Затем запустите `python tests/worker_smoke.py` из корня. Тест временно
останавливает Redis и worker и проверяет реальные повторные доставки.
